System wizualizacji historycznej mapy katastralnej gminy Czarna z XIX wieku. Składa się z trzech aplikacji webowych (mapa publiczna, panel admina, protokoły właścicieli), backendu FastAPI oraz launchera Tkinter, który jest jedynym zalecanym sposobem obsługi projektu.

Dane historyczne (działki, właściciele, demografia, genealogia, punkty historyczne) są przechowywane w SQLite lub PostgreSQL z PostGIS i eksponowane jako REST API. Frontend komunikuje się z backendem przez JSON HTTP, panel admina dodatkowo przez cookie session.

Stan testów (2026-06-05): 1126 testów automatycznych przechodzi, 9 pominiętych, 0 błędów. Testy obejmują backend, launcher i helpery instalacyjne PostgreSQL.

Architektura — Cztery Warstwy

System ma cztery logiczne warstwy, komunikujące się przez jasne interfejsy. Pełen opis w docs/technical/ARCHITECTURE.md.

  1. Frontend (przeglądarka) — static/mapa/ · static/admin/ · static/wlasciciele/
    Komunikuje się z backendem przez JSON REST (HTTP). Panel admina dodatkowo przez cookie session.
  2. Backend (FastAPI + uvicorn) — backend/main.py + lifespan + routers/ + services/ + auth/
    Cienkie I/O w routerach, logika biznesowa w services, bezpieczeństwo admina w auth/.
  3. Baza danych — SQLite (data/czarna.db) lub PostgreSQL + PostGIS
    SQLAlchemy 2.0 async: asyncpg dla PG, aiosqlite dla SQLite.
  4. Launcher (Tkinter GUI) — launcher/launcher_app.py + services/ + ui/ + config/ + utils/
    Uruchamia backend jako subprocess.Popen z env vars. Zarządza .env, miejscowościami, logami.

Kierunki importów (zależności)

Frontend — Trzy Niezależne Aplikacje

1. static/mapa/ — mapa publiczna

Interaktywna mapa katastralna renderowana przez MapLibre GL (WebGL, wektorowe kafle). Warstwy: działki, obiekty specjalne, infrastruktura, punkty historyczne (markery z galerią zdjęć).

  • Pliki: mapa.html + style.css + js/
  • Bez bundlerów — czysty ES6+ ładowany w kolejności zależności
  • API: window.MapV2 = Object.freeze({...})

2. static/admin/ — panel administracyjny

Wymaga logowania (cookie session przez backend/auth/). Sekcje: dashboard, właściciele, obiekty, demografia, genealogia, diagnostyka.

  • Pliki: admin.html + admin.css + admin.js + js/
  • Moduły: api.js, auth.js, dashboard.js, demography.js, diagnostics.js, genealogy-*.js
  • Kolejność ładowania skryptów w HTML: api → utils → notifications → moduły specyficzne → admin.js

3. static/wlasciciele/ — protokoły właścicieli

Publiczny widok protokołów hipotecznych. Read-only.

Konwencje JavaScript

  • Moduły rejestrują się w window jako Object.freeze({...})
  • Brak frameworków, bundlerów, npm. Czysty ES6+.
  • Polskie komentarze i etykiety UI, angielskie identyfikatory.
  • Fetch API do komunikacji z backendem.

Backend — FastAPI

Stack technologiczny

  • FastAPI >=0.109 + Uvicorn >=0.25
  • SQLAlchemy 2.0 async + Pydantic 2.0
  • asyncpg (PostgreSQL) + aiosqlite
  • psycopg2-binary (sync PG dla skryptów)
  • pytest >=8.0 + httpx
  • Pillow, requests, matplotlib

main.py — punkt wejścia

  • app = FastAPI(lifespan=lifespan) z własnym lifespan
  • Na starcie: assert_safe_secret_key() + init_db()
  • CORS z env CORS_ALLOWED_ORIGINS (w produkcji wymagane, w dev ["*"])
  • Kolejność rejestracji routerów: specyficzne → static_files (catch-all /{filename:path})
  • Tytuł API: "Mapa Katastralna Czarna API"

routers/ — 10 modułów, 53 endpointy

Cienkie I/O. Każdy router: schematy Pydantic + Depends(admin_required) + delegacja do services/.

  • admin.py (23) — CRUD właścicieli, obiektów, genealogii, demografii + dashboard + export-backup
  • static_files.py (13) — serwowanie plików statycznych, favicon, location-config.js, panel admina HTML
  • admin_auth.py (5) — auth-status, check-auth, login, logout, change-password
  • genealogy.py (4) — list, persons-format, pdf/{person_id}, /{klucz}
  • owners.py (3) — wlasciciele, wlasciciel/{klucz}, graph-data
  • map.py (2) — dzialki, map-config
  • stats.py (2) — stats, stats/rankings
  • diagnostics.py (1) — diagnostics
  • historical_points.py (1) — historical-points
  • editor.py (1) — save (zapis edycji)

services/ + auth/ + utils/

  • services/ — logika biznesowa. Czyste funkcje, bez Depends, DB przekazywany z routera.
  • auth/ — bezpieczeństwo admina. routes.py (login/logout/change-password) + security.py (walidacja SECRET_KEY, CORS hardening, network warnings).
  • utils/ — pdf_generator.py (eksport drzewa genealogicznego do PDF) + helpery.

Baza Danych — SQLite / PostgreSQL

Pełen opis: docs/technical/DATABASE.md.

Dwa tryby

  • SQLite (default): plik data/czarna.db. Zero konfiguracji.
  • PostgreSQL + PostGIS: dla środowisk produkcyjnych z dużą liczbą rekordów i zapytaniami przestrzennymi.

Pliki bazy w data/

  • czarna.db + czarna.db-shm + czarna.db-wal — baza główna (SQLite WAL)
  • locations.db — baza lokacji (lista miejscowości)
  • launcher_ui_settings.json — ustawienia UI launchera
  • locations/<miejscowosc>/ — folder per miejscowość z JSONami (genealogia, demografia, historical_points) + zdjęcia (history_photos/, point_photos/, protokoly/) + .env

Konfiguracja — backend/.env

# Tryb SQLite
DB_ENGINE=sqlite
DB_PATH=C:\...\Projekt Mapa Czarna\data\czarna.db
ACTIVE_LOCATION=Czarna

# Tryb PostgreSQL
DB_ENGINE=postgresql
DB_HOST=localhost
DB_PORT=5432
DB_NAME=mapa_czarna
DB_USER=mapa_user
DB_PASSWORD=...

Konwencja schematu

Tabele w kodzie mają krótkie nazwy bez prefixów (parcels, owners, demografia). Projekt nie planuje dzielenia bazy z innym systemem.

Launcher (Tkinter GUI)

Pełen opis: docs/technical/LAUNCHER.md.

Filozofia

Cały program opiera się na GUI — bez ręcznej edycji JSON / .env / SQL. Wszystkie akcje administracyjne mają odpowiednik w launcherze. Pliki .env i JSON edytowane są tylko przez launcher (z wyjątkiem tests/).

Sześć zakładek głównego okna

  • Aktywna miejscowość — wybór miejscowości + aktywacja (zapis do locations.db)

  • Centrum Zarządzania — kreator PostgreSQL, bazy danych, kalibracja mapy
  • Ustawienia Administratora — hasło admina, logi, konfiguracja sieci
  • Zaawansowane — kreator baz, edytor właścicieli/działek/genealogii
  • Diagnostyka — szybka diagnostyka + jakość danych + bezpieczeństwo admina

System Wielomiejscowości

Pełen opis: docs/technical/LOCATIONS.md.

Folder miejscowości

Każda miejscowość ma swój folder w data/locations/<nazwa>/:

  • .env — konfiguracja lokacji
  • demografia.json, genealogia.json, historical_points.json — dane
  • custom_icon.ico/.png, favicon.jpeg — branding
  • history_photos/, point_photos/, protokoly/ — foldery ze zdjęciami

Przełączanie miejscowości

Launcher ma zakładkę "Aktywna miejscowość" z listą. Wybór innej lokacji zapisuje wybór do data/locations.db i aktualizuje ACTIVE_LOCATION w backend/.env. Backend przeładowuje konfigurację przy kolejnym starcie.

Narzędzia

Edytory standalone tools/

Dedykowane aplikacje do masowej edycji danych historycznych.

  • tools/parcel_editor/ — edycja geometrii działek (folder)
  • tools/owner_editor.py — łączenie właścicieli, deduplikacja, genealogia (plik)
  • tools/genealogy_editor/ — drzewo genealogiczne + eksport PDF (folder)

Skrypty scripts/

  • install_pg_unattended.py — cicha instalacja PG 16 + PostGIS 3.6 (z UAC, z cleanup cache)
  • install_pg_gui.py — instalacja PG z paskiem postępu (7 kroków)
  • install_portable_pg.py — wersja portable PG (bez instalatora systemowego)
  • start_portable_pg.py / stop_portable_pg.py — start/stop portable PG
  • test_pg_portable_real_install.py — test realnej instalacji portable
  • uninstall_pg_system.py — deinstalacja z UAC + cleanup folderów 16_old_*

Auto-instalacja PostgreSQL (w launcherze)

  1. Pobiera instalatory z EDB/PostgreSQL.org jeśli brak w cache/
  2. Sprawdza poprzednią instalację (is_pg_install_healthy()); jeśli jest 16_old_*, przenosi i czyści
  3. Uruchamia instalator w trybie unattended z UAC
  4. Włącza PostGIS 3.6 z installer bundle
  5. Tworzy bazę mapa_czarna + włącza postgis
  6. Usuwa instalatory z cache (~457 MB zwolnione)

Czas: 2-5 min na świeżym Windows 10/11 z SSD.

Deinstalacja PostgreSQL

W "Centrum Zarządzania → Odinstaluj PostgreSQL":

  1. UAC prompt do deinstalatora Windows
  2. Po deinstalacji: _cleanup_pg_dirs() usuwa C:\Program Files\PostgreSQL\16 + wszelkie 16_old_*
  3. Reset konfiguracji PG w launcherze (przełącza na SQLite)
  4. Usuwa .postgres.env

Instalacja — Pierwsze Uruchomienie

Wymagania

  • Windows 10/11 (64-bit)
  • Python 3.11+ z python.org
  • Uprawnienia administratora (jeden raz, do instalacji PostgreSQL)
  • ~2 GB wolnego miejsca (z cache instalatorów + PostGIS bundle)

Pierwsze uruchomienie launchera

  1. Zainstaluj zależności: pip install -r requirements.txt
  2. Uruchom: python launcher/launcher_app.py
  3. Launcher tworzy backend/.env + data/czarna.db
  4. Uruchamia migrację schematu (idempotentna)
  5. Startuje backend (port 8000) i frontend w domyślnej przeglądarce

Wszystko automatycznie — zero ręcznej konfiguracji.

Przełączenie na PostgreSQL (opcjonalne)

Domyślnie SQLite wystarcza do pracy urzędnika z jedną miejscowością. Przełączenie na PG daje zapytania przestrzenne (PostGIS) i lepsze wsparcie dla wielu użytkowników. Wybór w launcherze → "Centrum Zarządzania" → kreator PG.
